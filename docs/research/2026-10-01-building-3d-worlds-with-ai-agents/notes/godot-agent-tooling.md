# Godot-specific agent tooling and practice: MCP servers, agent-built 3D projects, visual verification, engine facilities (2025–2026)

Research date 2026-10-01. Star counts, licences, release tags and push dates were read from the GitHub API on that date and are cited to the repository page. "Vendor" marks a source that sells a competing product. Model names (Fable 5, Opus 5.5, GPT-6 Astra and so on) are reported as the sources give them.

## 1. Which Godot MCP servers and agent integrations exist as of late 2026?

### Takeaway
There is no official Godot MCP server and no built-in AI support; the field is 100+ community servers of which roughly fifteen matter, and they differ mainly in whether the agent can observe and drive a *running game* (screenshot, input, live state) or only edit files and read the debug log. The most-starred server (Coding-Solo/godot-mcp) cannot take screenshots and has had no commits since April 2026; the free server with the most activity is hi-godot/godot-ai (MIT, Godot 4.7+), and the paid ones are cheap one-off purchases (Godot MCP Pro $15, GDAI MCP $19).

### Cited Findings

#### Landscape
- "There are now well over a hundred Model Context Protocol servers for Godot, most of them forks or weekend experiments"; the word "runtime" covers three different capabilities: file/editor-level (reads and writes `.tscn`/`.gd`, may launch the editor and read the console), editor-live (manipulates the open editor), and game-runtime (screenshots actual gameplay, injects input, runs GDScript against the live tree). A second axis is footprint: committed addon, custom engine, or a bridge injected transiently and removed on shutdown. Written by the author of one of the servers, last updated July 2026 — [Erodenn comparison](https://github.com/Erodenn/godot-mcp-runtime/blob/main/docs/comparison.md)

#### Integrations that are not plain MCP servers
- godogen (7,033 stars, MIT, pushed 2026-09-26) publishes a thin runtime into a fresh game repository — a manifest, a one-page engine guide and an asset-generation skill — as `CLAUDE.md` + `.claude/skills/` for Claude Code or `AGENTS.md` + `.agents/skills/` for Codex; it uses no MCP server — [godogen](https://github.com/htdt/godogen)
- Ziva is a closed-source in-editor agent: free with the user's own Claude/ChatGPT subscription or a local model, $20/month Basic, $50/month Pro (adds a "Playtest Agent"); the vendor says it can also act as an MCP server for Claude Code, Codex and Cursor (vendor) — [Ziva roundup, updated 2026-09-27](https://ziva.sh/blogs/best-ai-tools-for-godot-2026)
- Summer Engine is a proprietary Godot-based engine with built-in AI: Free app, Pro $20/month, Pro+ $60/month, Ultra $200/month, account required — [Summer Engine pricing](https://www.summerengine.com/pricing); a competitor lists it as "macOS/Windows only" (vendor) — [Ziva roundup](https://ziva.sh/blogs/best-ai-tools-for-godot-2026)
- StraySpark sells a commercial Godot MCP Server from $39.99 (vendor) — [StraySpark guide, 2026-05-15](https://www.strayspark.studio/blog/godot-mcp-setup-claude-code-2026)
- godot-claude-harness is a Claude Code plugin that checks work against the installed engine with the editor closed: `gd api <Class>` reads a `--doctool` dump of the user's binary, `gd check` runs the real GDScript parser, and a `PostToolUse` hook runs that check on every `.gd` file Claude writes and "blocks the turn"; it describes itself as "the other half of godot-ai" (0 stars, created 2026-08-18) — [godot-claude-harness](https://github.com/DavidMGDev/godot-claude-harness)

#### Official support
- The Godot Foundation's contribution policy of 30 June 2026 bans autonomous AI agents, "vibe coding" and substantial AI-generated code in contributions *to the engine*, allows AI for "menial things (like code completion, regex, or find and replace)", and says nothing about MCP, editor AI features or using AI to make games — [Changes to our Contribution Policies](https://godotengine.org/article/contribution-policy-2026/)
- A January 2026 proposal to integrate an LLM into the editor remains open with engine contributors replying "I don't think this makes sense in Godot itself. However, it is something that can definitely be done via addons" (dsnopek, who links godai, ee0pdt/Godot-MCP and Coding-Solo/godot-mcp) and "There have been many proposals about adding official LLM support to Godot, and they have consistently received negative feedback from the community" (Meorge, listing the earlier proposals) — [godot-proposals #14090](https://github.com/godotengine/godot-proposals/issues/14090)
- A May 2025 "Built-in AI" proposal was closed the same day as a duplicate; one commenter noted that with MCP "this is something that doesn't need to be embedded" — [godot-proposals #12491](https://github.com/godotengine/godot-proposals/issues/12491)
- What the engine does ship is a GDScript language server and debug adapter, selectable with `--lsp-port` and `--dap-port`, which third-party servers bridge — [command line tutorial](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)
- Community reception on the official forum is cool: an announcement thread for an MCP tool drew the reply "the Object of the exercise is to programme stuff myself" — [Godot MCP Studio thread, 2026-09-20](https://forum.godotengine.org/t/godot-mcp-studio-an-ai-tool-for-godot-4/144463); a hobbyist's AI-built 3D shooter thread drew "Love that but im only sad that theres ai" — [Drone Kill thread, 2026-07-03](https://forum.godotengine.org/t/3-d-ego-shooter-on-the-way-drone-kill/141185)

### Inferences
- For a project whose scene is built in code at run time (as Agentnagar's is), editor-authoring tools (create node, set property, build layout) have little to act on; the value is in the game-runtime tier: screenshot, frame recording, live state, input, deterministic stepping. Coding-Solo's server adds almost nothing over running `godot` from the shell, which is what its most detailed user actually reported using it for.
- Candidates that fit a Linux desktop, Godot 4.7, GDScript and a public repository: hi-godot/godot-ai (free, Godot 4.7+, but a committed addon, a Python server, default-on telemetry and visible churn), Erodenn/godot-mcp-runtime (nothing committed, off-screen background window), satelliteoflove/godot-mcp (deterministic stepping and JSON state), and Godot MCP Pro ($15) if on-disk frame recording and screenshot comparison are wanted. GDAI MCP's instruction not to commit the plugin to a public repository is awkward for an open-source project. Summer Engine is not an option on Linux if the competitor's platform note is right.
- The servers that advertise spatial data (GodotIQ `scene_map`/`spatial_audit`, Beckett `render_probe`, satelliteoflove state digests) all exist because screenshots alone proved an expensive and unreliable way to answer "is this object where I think it is"; the same checks can be written as project-local GDScript probes without any MCP server.
- Server choice carries supply-chain risk: these tools execute arbitrary GDScript, several are weeks or months old, and the most-starred one needed two remote-code-execution fixes in 2026.

### Gaps
- No Reddit evidence: r/godot, r/ClaudeAI and r/ClaudeCode could not be read (HTTP 403 from this environment), so user sentiment is drawn from Hacker News, GitHub issues and the Godot forum only.
- No independent benchmark compares the servers on the same task; capability claims come from each project's README and are not audited. GDAI MCP and Godot MCP Pro are closed source, so their runtime mechanisms were not inspected.
- No source states how many people use any of these servers; stars track age and reach, not capability.
- I found no Codex-specific report on a named Godot MCP server beyond client-compatibility tables.

## 2. Which documented 3D Godot projects were built largely with coding agents?

### Takeaway
The documented agent-built 3D Godot projects are arcade-scale games built in hours to days; the better-looking ones keep the human as art director, the best-documented ones assemble scenes in code or by script rather than in the editor, and assets come from image-to-3D generators, texture generators, bought or free kits, or Blender driven by Python. Their authors report the same weak points: rigging and animation, mesh details the agent cannot see (winding, splitting, scale), performance, and output that reads as lifeless without human taste. No documented example reaches city scale with demonstrated visuals.

### Cited Findings

#### godogen demos (GitHub user "htdt", March 2026 onwards)
- Visuals: a demo reel; the 3D prompts are a topographic-map racing game ("CartoRally"), an "ultra realistic" riverbank scene with shader water and grass, and an Alpine snowboard simulator — [demo video](https://youtu.be/eUz19GROIpY), [demo prompts](https://github.com/htdt/godogen/blob/master/docs/demo_prompts.md)
- Assets and animation: Gemini or xAI Grok for images, Tripo3D for image-to-3D and rigged biped animation, Grok video for animated sprites; since 2026-09-22 custom humanoid move sets are generated locally with NVIDIA Kimodo and baked to ordinary glTF clips — [godogen README](https://github.com/htdt/godogen), [changelog](https://github.com/htdt/godogen/blob/master/CHANGELOG.md)
- Workflow: scenes are generated at build time by headless `SceneTree` scripts that build the node graph and serialise a `.tscn`; the running game is captured with Movie Maker and the agent "judges results from the running game … not from a clean compile" and must finish with a 15–20 s video which it watches back — [engine guide](https://github.com/htdt/godogen/blob/master/engines/godot.md), [runtime manifest](https://github.com/htdt/godogen/blob/master/prompts/runtime.md)
- Stated cost: LLM usage "probably around $1–3 for a full game generation run if you were paying API rates" (run on a Claude Max subscription); images 5–15 cents, Tripo3D models 30–60 cents, "total asset costs usually land under $3"; the snowboarding game "roughly $5–8 all-in"; "A full generation run can take hours" — [author's HN comment, 2026-03-17](https://news.ycombinator.com/item?id=47410455), [godogen README](https://github.com/htdt/godogen)
- What went wrong, per the author: "three specific engineering bottlenecks" — GDScript knowledge, build-time versus run-time state ("every node needs its owner set correctly or it silently vanishes on save"), and evaluation ("A coding agent is inherently biased toward its own output"); the project migrated all generated code from GDScript to C# on 2026-04-06, and by 2026-07-02 deleted its planner, scaffold, API-lookup and quirks skills as "guidance the current model no longer needs" — [Show HN post, 2026-03-16](https://news.ycombinator.com/item?id=47400868), [changelog](https://github.com/htdt/godogen/blob/master/CHANGELOG.md)
- What went wrong, per viewers (337 points, 205 comments): "they felt really lifeless to me … the mechanics, and movements of the character, made it seem like it's really bad physics"; "The games in the video look like GameJam projects"; the author answered "these demos are essentially raw single-run output, not cherry-picked or polished" — [Show HN thread](https://news.ycombinator.com/item?id=47400868), [HN comment](https://news.ycombinator.com/item?id=47406299), [author's reply](https://news.ycombinator.com/item?id=47404136)

#### TRON: EXONIX (Stefan Vaskevich, July 2026)
- Visuals: playable web demo, repository screenshots and a 20-minute build video (39k views on 2026-10-01) — [demo](https://www.top3d.ai/demo/exonix), [repository](https://github.com/witnesstodark/tron-exonix), [video, 2026-07-24](https://www.youtube.com/watch?v=B0gGJyl9G_M)
- Setup: Godot 4.7 Forward+; "The whole scene is built in code — one `.tscn`, everything else is scripts"; Claude Code with Coding-Solo's Godot MCP, Blender MCP and fal.ai — [repository README](https://github.com/witnesstodark/tron-exonix)
- Assets: floor PBR sets from flat albedo images through fal.ai PATINA, emission maps from an image-edit model, an HDRI sky, Tripo image-to-3D for the saw, pickups and five obstacle monuments, generated music and sound; textures and models load at run time from outside `res://` — [CLAUDE.md](https://github.com/witnesstodark/tron-exonix/blob/master/CLAUDE.md), [repository README](https://github.com/witnesstodark/tron-exonix)

### Inferences
- Agentnagar's current method — Blender driven by agent-written Python, scenes assembled in code — is the same method used by the two most comparable 2026 builds ("Can It Code?" and Go Go Slime) and by Exonix for scene assembly. What those projects add, and Agentnagar's description lacks, is (a) a fixed visual reference or palette made before building, (b) a separate judging pass per round, (c) generated or photographic textures and human-tuned materials rather than flat colours, and (d) explicit lighting passes.
- Every project that shows characters either buys rigging/animation from a generator (Tripo, Kimodo) or avoids skeletons altogether (the 41-part astronaut); none reports an agent hand-authoring a good skinned walk cycle in Blender Python. This matches the HN report that rigging is "the hardest thing" in the loop.
- Engine facilities for dense environments (GridMap, MultiMesh, visibility ranges, import scripts) are almost absent from these write-ups — Desert Velocity's LODs and MultiMesh are the only mention — which is consistent with the observation that agents default to instantiating everything in code.

- No independent assessment of visual quality exists for any of these projects; view counts are not quality evidence.
- I found no documented agent-built Godot project at city scale with visuals. The GodotIQ city is a claim without media.
- Many popular "AI built a 3D game" videos use Unreal, Unity or three.js rather than Godot and were excluded.

## 3. Closing the visual loop in Godot: stills and motion

### Takeaway
`--headless` cannot produce pixels in Godot 4.7 — it swaps in a dummy rasteriser, and combining it with `--write-movie` crashes — so every working recipe uses a real or virtual display with a real renderer and then either reads the viewport texture or uses Movie Maker (`--write-movie frame.png --fixed-fps N --quit-after M`), which also yields deterministic frame sequences for motion. The evidence on vision-model critique is mixed: it catches gross defects and placement laziness, but a 2025 benchmark puts visual-regression accuracy at 45% and temporal localisation in video at about 35%, the most experienced Godot practitioner dropped his separate Gemini judge in April 2026, and his animation pipeline now relies on numeric gates first and contact sheets second.

### Cited Findings

#### What `--headless` can and cannot do
- `--headless` is defined as "`--display-driver headless --audio-driver Dummy`. Useful for servers and with `--script`" — [command line tutorial](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)
- "The `--headless` command line argument allows Godot not to spawn a window (and not require a GPU), but it disables all rendering code"; the proposal for an `--offscreen` mode has been open since 2022-11-15 — [godot-proposals #5790](https://github.com/godotengine/godot-proposals/issues/5790)
- The draft implementation (Vulkan only, works with `--write-movie`) has been an open pull request since 2024-07-19; a second attempt from 2026-05-10 was closed — [godot PR #94530](https://github.com/godotengine/godot/pull/94530), [godot PR #119379](https://github.com/godotengine/godot/pull/119379)
- "This is needed in order to render for AI iteration visual feedback iteration cycles. Godot cannot do this headlessly today. --headless swaps in a dummy driver that disables rendering outright, so a capture script does not fail — it hangs, awaiting a frame that will never draw." (2026-08-16); another user maintains a small fork adding a `--hidden` window mode because headless also disables the shader baker — [godot-proposals #5790](https://github.com/godotengine/godot-proposals/issues/5790)
- "adding `--headless` to `--write-movie` aborts (`Parameter "t" is null`)" — [godogen engine guide](https://github.com/htdt/godogen/blob/master/engines/godot.md)
- A September 2026 project plan records the "hard constraint: True `--headless` cannot capture pixels. Required approach uses Xvfb + OpenGL renderer + `Viewport.get_texture().get_image()` or Movie Maker PNG output", and lists "Vulkan/lavapipe-on-Xvfb as default CI" among rejected options — [fragr PR #30, 2026-09-18](https://github.com/blisspixel/fragr/pull/30)
- Headless mode is still the right tool for everything that does not need pixels: `--import`, `--check-only`, `--script`, exports and tests — [command line tutorial](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)

#### Capturing stills
- The documented capture call is `get_viewport().get_texture().get_image()`; "if you use this in `_ready()` or from the first frame of the Viewport's initialization, you will get an empty texture", so wait with `await RenderingServer.frame_post_draw`. A SubViewport is a render target whose texture can be read the same way, and its Update Mode can be set to `Once` to "render an image once" — [Using Viewports](https://docs.godotengine.org/en/stable/tutorials/rendering/viewports.html)
- A reusable harness: an autoload `screenshotter.gd` waits N physics frames, awaits `frame_post_draw`, saves the viewport image and quits; it is run as `xvfb-run -a godot --path . --rendering-driver opengl3 <scene> -- shot <out.png> [frames]` with the project set to `gl_compatibility`, while unit tests run under `--headless`; the author notes software rendering "is slow, so anything that needs true frame rate profiling wants real hardware" — [godot-game-harness](https://github.com/jonathancaruso/godot-game-harness), [write-up, 2026-07-08](https://www.jonathancaruso.com/blog/getting-claude-code-to-build-games-in-godot)
- godogen's wrapper uses `xvfb-run -a -s '-screen 0 1920x1080x24'` only when neither `DISPLAY` nor `WAYLAND_DISPLAY` is set, forces the NVIDIA Vulkan ICD when `/usr/share/vulkan/icd.d/nvidia_icd.json` exists, and runs Forward+; "Without a hardware GPU, screenshots can still work via software Vulkan (`llvmpipe`/`lavapipe`), but video capture should be skipped" — [godogen capture guide at commit 144dba5, 2026-04-16](https://github.com/htdt/godogen/blob/144dba545a5facaf073ff0166cbfbc18f7d9cdce/claude/skills/godogen/capture.md)
- One MCP server avoids a virtual display by moving a real, borderless, unfocusable game window to (-9999, -9999) — [godot-mcp-runtime README](https://github.com/Erodenn/godot-mcp-runtime)
- godot-ai can render a "cinematic" Camera3D view of the edited scene as well as the editor viewport and running game — [godot-ai TOOLS.md](https://github.com/hi-godot/godot-ai/blob/main/docs/TOOLS.md)

#### Movie Maker for deterministic sequences
- "Godot can record non-real-time video and audio from any 2D or 3D project"; the reported `delta` is identical across frames "regardless of how long it actually took to render the frame"; built-in writers are OGV (Theora/Vorbis, editor builds only), AVI (MJPEG, 4 GB limit) and a PNG sequence with WAV; `--write-movie`, `--fixed-fps` and `--quit-after N` are available from the command line and in exported projects; with the `disabled` or `canvas_items` stretch modes the output resolution is the window size — [Creating movies](https://docs.godotengine.org/en/stable/tutorials/animation/creating_movies.html), [MovieWriter class](https://docs.godotengine.org/en/stable/classes/class_moviewriter.html)
- godogen's recipe: `godot --write-movie screenshots/result/frame.png --fixed-fps 30 --quit-after 450 --script test/Presentation.cs`, then ffmpeg to H.264; "`--fixed-fps` makes motion deterministic (450 frames @30fps = 15s). Pre-position the camera … (the first movie frame renders before `_Process`). Drive capture-time input from the script, not live keys." — [godogen engine guide](https://github.com/htdt/godogen/blob/master/engines/godot.md)
- Frame-rate guidance from the same project: static scenes use `--fixed-fps 1` with one frame per camera view ("8 frames for a camera orbit"); dynamic scenes use `--fixed-fps 10` because "Low FPS breaks physics — `delta` becomes too large, causing tunneling and erratic behavior" — [godogen capture guide at commit 144dba5](https://github.com/htdt/godogen/blob/144dba545a5facaf073ff0166cbfbc18f7d9cdce/claude/skills/godogen/capture.md)
- GDScript-specific trap: "`await get_tree().process_frame` advances the movie frame counter each tick. A single await takes many movie frames, not 1. Use `_init_frames` counter in `_physics_process()` instead of await chains" — [godogen GDScript-era quirks at commit 93013e1, 2026-04-03](https://github.com/htdt/godogen/blob/93013e1dc4a96785794e44a691dd48d3da3ee9da/skills/godogen/quirks.md)
- PNG movie writing was sped up in a July 2026 merge ("Speed up PNG MovieWriter by saving with `PNG_IMAGE_FLAG_FAST`") — [godot PR #121437](https://github.com/godotengine/godot/pull/121437)
- `--disable-render-loop` makes "rendering only occur when called explicitly from script" — [command line tutorial](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)

#### Image diff and visual regression
- "Godot has no built-in visual-regression testing"; the dedicated tools I found are tiny: `godot-visual-regression` (npm CLI: boots the main scene, captures after 90 frames, diffs against a baseline with a 2% changed-pixel threshold and writes a red heat-map; 0 stars) and `godot-vrt` (a capture addon that leaves comparison to "Argos CI, reg-suit, or pixelmatch"; 1 star) — [godot-visual-regression](https://github.com/CregSutherdale/godot-visual-regression), [godot-vrt](https://github.com/KantaiMishima/godot-vrt)
- The engine's own rendering test scenes live in a personal repository with 9 stars — [Calinou/godot-rendering-tests](https://github.com/Calinou/godot-rendering-tests)
- Screenshot comparison is otherwise bundled into MCP servers: `compare_screenshots` in Godot MCP Pro and Beckett Full, `compare-render-screenshots` in Godot-MCP-Native, and a pixel diff in godot-mcp-enhanced (RGB distance threshold 0.12, returns changed-pixel ratio and bounding box; the author reports a diff ratio of 0.1762 for a good pair against 0.4797 for an image with its lower half missing) — [Godot MCP Pro README](https://github.com/youichi-uda/godot-mcp-pro), [Godot-MCP-Native README](https://github.com/yurineko73/Godot-MCP-Native), [godot-mcp-enhanced README](https://github.com/wgt19861219/godot-mcp-enhanced)
- General-purpose diff tools that are scriptable: odiff (MIT, 3,223 stars), pixelmatch (ISC, 6,974 stars), NVIDIA FLIP for perceptual error maps of rendered images (651 stars) — [odiff](https://github.com/dmtrKovalenko/odiff), [pixelmatch](https://github.com/mapbox/pixelmatch), [FLIP](https://github.com/NVlabs/flip)
- A cheap non-vision check proposed for one server: a `render` validation that runs a short `--write-movie` capture with the real renderer and answers "does the frame show rendered content rather than a near-uniform blank?", because a screenshot tool that returns only `{path, width, height}` makes "a fully rendered frame and a completely blank one yield identical successful responses" — [godot-mcp-runtime PR #63, 2026-09-24](https://github.com/Erodenn/godot-mcp-runtime/pull/63)

#### Letting a vision model critique frames against reference art
- godogen's earlier pipeline generated a "visual target" first: one 16:9 image that "must look like an in-game screenshot, not concept art", enumerating every game object and excluding effects the game will not implement ("Volumetric lighting, motion blur, depth of field … skip unless the game actually implements them"), because "every spatial and stylistic choice you bake in here becomes a requirement downstream" — [visual-target skill at commit 144dba5](https://github.com/htdt/godogen/blob/144dba545a5facaf073ff0166cbfbc18f7d9cdce/claude/skills/godogen/visual-target.md)
- Its visual-QA skill ran in a forked context, sent reference plus screenshots to `gemini-3-flash-preview` by default (or Claude vision, or both with the stricter verdict winning), never saw code, and was told "Your job is to find problems, not confirm things look fine". Criteria: grid/uniform placement where the reference is organic, uniform scale, flat composition, stretched materials, z-fighting, clipping, floating objects, shadow artefacts, impossible orientations, scale mismatches, untextured primitives and default grey materials — [visual-qa skill at commit 144dba5](https://github.com/htdt/godogen/blob/144dba545a5facaf073ff0166cbfbc18f7d9cdce/claude/skills/visual-qa/SKILL.md)
- That external judge was then removed: "Dropped Gemini verification — Opus 4.7 / GPT 5.5 self-verify from captured frames; external pass added no signal" (2026-04-26) — [godogen changelog](https://github.com/htdt/godogen/blob/master/CHANGELOG.md)
- An HN commenter judged the original separation sound: "using a model that sees only screenshots and never the code is a genuinely good idea for avoiding confirmation bias" — [Show HN thread](https://news.ycombinator.com/item?id=47400868)
- godot-ai offers "Vision Routing": a screenshot is sent to a separate vision model (suggested: a Groq-hosted Qwen model, Gemini Flash or Grok) and the agent receives a text description instead of the image; it exists for text-only models and is off by default — [vision-routing doc](https://github.com/hi-godot/godot-ai/blob/main/docs/vision-routing.md)
- A screenshot can mislead: in the 99-minute 3D build, back-face culling removed the whole terrain while "visible was true, the AABB was correct, the node was in the remote tree, the log was clean, it ran at 120 fps. The screenshot showed sky below the horizon, which reads convincingly as ground, so the next half hour went into fog, exposure and palette adjustments on geometry that had never rendered a single frame." The fix was a data probe plus debug-draw modes (unshaded, wireframe, overdraw, normal buffer) "so a single screenshot eliminates whole classes of cause" — [Beckett forum post, 2026-07-29](https://forum.godotengine.org/t/beckett-zero-sidecar-mcp-server-for-godot-4-2-the-ai-sees-and-optionally-playtests-your-game/141177/7)
- Benchmark evidence (16 models of early-to-mid 2025, 2,236 image and 1,200 video samples from real games): best accuracy was 82.8% on image glitch detection but only 53.0% on visual unit tests, 45.2% on visual regression and 54.0% on bug-report generation; "Visual regression testing with VLMs does not yet perform well", models struggle with "unusual body configurations", "intricate object clipping" and fine detail, and "high false-positive rates continue to pose a significant issue" — [VideoGameQA-Bench, arXiv 2505.15952v2](https://arxiv.org/html/2505.15952v2) (first posted 2025-05-21; the models tested are now a generation old)
- Claude's documented image limits: cost is ⌈width/28⌉ × ⌈height/28⌉ visual tokens; Claude 4.7 and later accept up to 2576 px on the long edge and 4,784 visual tokens per image (a 1920×1080 frame is 2,691 tokens, a 3840×2160 frame is downscaled to 2576×1449), other models 1568 px and 1,568 tokens; with more than 20 images in a request each must be at most 2000 px per side; animated GIFs use only the first frame; "Claude's coordinate and localization outputs are approximate" and counts of many small objects may be inaccurate; label multiple images "Image 1:", "Image 2:" and put images before text — [Claude vision docs](https://platform.claude.com/docs/en/build-with-claude/vision)
- Practitioners' stated limits: "This is not a playtesting replacement. It doesn't catch the subtle feel issues that only a human notices" — [godot-mcp-runtime README](https://github.com/Erodenn/godot-mcp-runtime); in Exonix the human, not the model, confirmed materials — [tron-exonix CLAUDE.md](https://github.com/witnesstodark/tron-exonix/blob/master/CLAUDE.md)

#### Reviewing motion and animation
- godogen's dynamic mode sent the reference image plus frames "0.5 seconds apart (2 FPS cadence), covering the full scene duration" and asked for: stuck entities, jitter or teleportation, sliding ("position changes but animation pose stays frozen (ice-skating)"), physics breaks, animation mismatches ("walk animation at running speed, idle while moving"), camera jumps and collision failures; "Motion-timing and state-handoff bugs are the primary failures to catch here — broad art similarity with the reference is secondary and often matches even when the motion is broken" — [dynamic prompt at commit 144dba5](https://github.com/htdt/godogen/blob/144dba545a5facaf073ff0166cbfbc18f7d9cdce/claude/skills/visual-qa/scripts/dynamic_prompt.md)
- The same author's later animation pipeline puts numbers first: "Intrinsic checks catch a broken limb; only relational checks catch a broken pose"; "Gate a derivative, not only per-frame poses. 'The hands move abruptly' is not a property of any frame — every one is a legal pose"; "skewed fists/feet from a wrong rest anchor read fine in stills and are ~free to catch mechanically"; "timing regressions are invisible to pose-space QA", so "re-watch one hit per attack at game speed after any speed retune" — [godogen motion guide](https://github.com/htdt/godogen/blob/master/asset-gen/motion.md)
- Its numeric gates for a scripted, seeded run: no NaN in pose or position; locomotion travel above a floor with the correct sign; hip-height deltas for jump, crouch and knockdown; one-shot clips not interrupted; per-tick worst bone rotation step at most about 80° outside cross-fades ("genuine flips show as 90–180° single-tick spikes on ONE bone") — [kimodo-practical INTEGRATE.md](https://github.com/htdt/kimodo-practical/blob/main/INTEGRATE.md)
- Its visual rubric, applied after the gates: "Render every move on a certified character (contact sheet + video) and check: the prompted apex actually visible and at the intended amplitude? feet planted during stances/guards (no skate)? no wrist flips or knee pops? root travel matches intent?"; and before baking, "Always verify visually with a stick-figure filmstrip on the canonical skeleton"; contact sheets per move, with "consecutive-tick close-ups for anything the metrics flag" — [kimodo-practical BAKE.md](https://github.com/htdt/kimodo-practical/blob/main/BAKE.md), [INTEGRATE.md](https://github.com/htdt/kimodo-practical/blob/main/INTEGRATE.md)
- Its most expensive Godot bug was a harness that did not drive the character the way the game does: "the gate scrubbed clips through the raw player (`Play(clip, 0.0)`), the game seeked them through a crossfading wrapper, and Godot drains a crossfade off the mixer delta — which a seeked clip freezes. Every seeked beat of the run played the *previous* move, for its whole length, and every gate passed." — [godogen motion guide](https://github.com/htdt/godogen/blob/master/asset-gen/motion.md)
- Budget: "A gated 17-move set generates in ~10 minutes on a 12 GB GPU … the time goes to the review loop: filmstrip/QA review → adjust prompts or spec → regenerate → re-certify" — [godogen motion guide](https://github.com/htdt/godogen/blob/master/asset-gen/motion.md)
- Video-capable models: Gemini samples video at 1 frame per second by default and warns that "Fast action sequences might lose detail due to the 1 FPS sampling rate"; a custom `fps` and clip offsets can be set; each frame costs 258 tokens at default resolution or 66 at low, about 300 or 100 tokens per second of video; inline upload is limited to 100 MB — [Gemini video understanding, updated 2026-09-23](https://ai.google.dev/gemini-api/docs/video-understanding)
- Benchmark evidence on video: best accuracy 78.1% for video glitch detection, 52.0% for video bug reports, and only 35–36% for finding the frame where a glitch occurs ("needle in a haystack") — [VideoGameQA-Bench](https://arxiv.org/html/2505.15952v2)
- Tools that make motion observable without pixels: freezing and stepping the game clock with inputs inside the step — [satelliteoflove/godot-mcp](https://github.com/satelliteoflove/godot-mcp); frame-timed input sequences whose basis is frames, "not milliseconds … that's what reproduces identically across runs" — [godot-ai TOOLS.md](https://github.com/hi-godot/godot-ai/blob/main/docs/TOOLS.md); recording property values over time (`monitor_properties`) and `capture_frames` — [Godot MCP Pro README](https://github.com/youichi-uda/godot-mcp-pro); a `--drive` flag for scripted button input used to measure jump arcs — [Babylonian Twins blog](https://babyloniantwins.com/blog/porting-a-1993-amiga-game-to-godot/)

### Inferences
- Local verification on the target machine (run by this researcher in a scratch project outside the repository, Godot 4.7.2.stable.arch_linux, 2026-10-01; not a web source): `godot --headless --script capture.gd` reports display server `headless`, and `root.get_texture().get_image()` returns null with `ERROR: Parameter "t" is null` at `servers/rendering/dummy/storage/texture_storage.h:110`; `godot --headless --write-movie frame.png --fixed-fps 30 --quit-after 5` prints "Movie Maker mode enabled", the same error, then crashes with signal 11 and leaves only an empty `frame.wav`. `godot --help` lists the `headless` display driver with only the `dummy` rendering driver. This reproduces the godogen and fragr statements exactly.
- State of the laptop relevant to capture (checked, not changed): `ffmpeg`, `kwin_wayland`, `Xwayland`, `vulkaninfo` are installed; `Xvfb`/`xvfb-run`, `weston`, `cage`, `gamescope` and ImageMagick are not; the only Vulkan ICD is NVIDIA's (no lavapipe). So the published Xvfb recipes need a package install, and the software-Vulkan fallback is unavailable; today the only working path is the one the project already uses — a real window on the desktop session.
- `--write-movie` with a PNG sequence is the missing piece for motion: it gives frame-exact, hardware-independent sequences from the existing `extends SceneTree` probe scripts, at a chosen `--fixed-fps`, without a screen recorder. Because Agentnagar's simulation core is deterministic, a fixed-FPS capture of a scripted run is reproducible, which makes both pixel diffs and numeric gates meaningful.
- Contact-sheet arithmetic for Claude's high-resolution tier: one 2576×1449 sheet costs at most 4,784 tokens and holds, for example, 4×3 frames at about 644×483 each; twelve separate 960×540 frames cost 35×20 = 700 tokens each, 8,400 in total, at higher per-frame resolution. For Gemini, a 10-second clip sampled at 10 fps is about 100 frames × 258 = 25,800 tokens. Sampling at the default 1 fps shows about one pose per one-second walk cycle and cannot reveal foot sliding; even godogen's 2 fps cadence was aimed at stuck, teleporting or sliding entities, not at the quality of a gait.
- The evidence supports a layered order of checks, cheapest first: numeric gates on simulation and skeleton state (position deltas, foot speed relative to ground while planted, bone rotation steps), a non-blank "heartbeat" on the frame, debug-draw views, pixel diff against a stored baseline for regressions, then a vision critique against reference art for composition and density, then the human for taste. Vision models are weakest exactly where pixel diffs are strongest (regression) and strongest where diffs are useless (comparing against concept art).
- A reference image phrased as an achievable in-engine screenshot, enumerating the objects to be built, is a more usable judging target than concept art; concept sheets contain lighting and atmosphere the renderer will not reproduce, which makes every comparison fail in ways the agent cannot act on.

### Gaps
- No published measurement compares contact sheets, frame strips and video-model input for judging game animation, in Godot or elsewhere; the only quantitative evidence is the 2025 benchmark on older models.
- I found no report of anyone feeding Godot capture video to Gemini at a custom frame rate and measuring the result.
- Whether Godot under Xvfb can present with NVIDIA's Vulkan ICD on this laptop is untested. godogen's recipe assumes it works on GPU servers; fragr rejected Vulkan-on-Xvfb for CI. A nested or virtual Wayland compositor (for example `kwin_wayland --virtual`) could not be tried: the binary is killed inside this sandbox.
- No source documents Godot capture under a headless Wayland compositor (weston, cage, gamescope).
- The Godot documentation page on Movie Maker does not itself state that it cannot run headless; that fact comes from the proposal thread, practitioners and the local test.

## 4. Which Godot facilities build rich environments from data rather than hand-rolled code?

### Takeaway
The engine already contains what a kit-assembled city needs, all scriptable from GDScript: GridMap with a MeshLibrary (cells batched into one MultiMesh per item per octant, with collision and navigation), MultiMesh for scattered props, import-time automation (name suffixes, per-node import settings, `EditorScenePostImport`, multi-file reimport), automatic mesh LOD, visibility ranges for hierarchical LOD and CPU occlusion culling. The Compatibility renderer — the only one on the web — lacks decals, light projectors, SSR, volumetric fog, depth of field, FXAA/SMAA/TAA, compositor effects, the normal-roughness buffer and automatic instancing, and renders to an 8-bit target.

### Cited Findings

#### GridMap and MeshLibrary
- "GridMap lets you place meshes on a grid interactively. It works both from the editor and from scripts"; each MeshLibrary tile is "a mesh with materials plus optional collision and navigation shapes"; "Internally, a GridMap is split into a sparse collection of octants for efficient rendering and physics processing"; cells are set from code with `set_cell_item(position, item, orientation)` using one of 24 orthogonal orientations — [GridMap class](https://docs.godotengine.org/en/stable/classes/class_gridmap.html)
- In the 4.7 source each octant creates one RenderingServer MultiMesh per item type (`multimesh_create`, `multimesh_allocate_data`, `multimesh_set_mesh`) — [grid_map.cpp, 4.7 branch](https://github.com/godotengine/godot/blob/4.7/modules/gridmap/grid_map.cpp#L816-L837)
- A MeshLibrary is authored as a scene with a Node3D root and MeshInstance3D children (each may have one StaticBody3D with collision shapes and one NavigationRegion3D) and exported with Scene > Export As > MeshLibrary; `bake_navigation` creates a navigation region per cell — [Using GridMaps](https://docs.godotengine.org/en/stable/tutorials/3d/using_gridmaps.html)
- MeshLibrary can also be filled from code: `create_item`, `set_item_mesh`, `set_item_mesh_transform`, `set_item_mesh_cast_shadow`, `set_item_shapes`, `set_item_navigation_mesh`, `set_item_preview` — [MeshLibrary class](https://docs.godotengine.org/en/stable/classes/class_meshlibrary.html)
- Limitation: "GridMap doesn't extend VisualInstance3D and therefore can't be hidden or cull masked based on `VisualInstance3D.layers`"; `make_baked_meshes` produces merged meshes for LightmapGI — [GridMap class](https://docs.godotengine.org/en/stable/classes/class_gridmap.html)
- Recent changes: rotate selected cells and rendering optimisations (4.5), Bresenham line painting (4.6), octant querying, collider display, cursor coordinates and a dedicated MeshLibrary editor (4.7) — [4.5 changelog](https://github.com/godotengine/godot/blob/4.5/CHANGELOG.md), [4.6 changelog](https://github.com/godotengine/godot/blob/4.6/CHANGELOG.md), [4.7 changelog](https://github.com/godotengine/godot/blob/4.7/CHANGELOG.md), [4.7 release page](https://godotengine.org/releases/4.7/)
- Coding-Solo's server has an `export_mesh_library` tool and Godot MCP Pro has `add_gridmap` and `get_gridmap_info` — [Coding-Solo README](https://github.com/Coding-Solo/godot-mcp), [Godot MCP Pro README](https://github.com/youichi-uda/godot-mcp-pro)

#### MultiMesh and scattering
- "A MultiMesh is a single draw primitive that can draw up to millions of objects in one go"; the drawback is that "there is no screen or frustum culling possible for individual instances … A workaround is to create several MultiMeshes for different areas of the world"; `visible_instance_count` limits how many are drawn; per-instance colour and custom data are available to shaders — [Optimization using MultiMeshes](https://docs.godotengine.org/en/stable/tutorials/performance/using_multimesh.html) (page flagged outdated by the docs team)
- Automatic instancing of MeshInstance3D nodes that share mesh and material "is only implemented in the Forward+ renderer, not Mobile or Compatibility", and only for opaque or alpha-tested materials; otherwise "you must use MultiMesh" — [Optimizing 3D performance](https://docs.godotengine.org/en/stable/tutorials/performance/optimizing_3d_performance.html)
- All instances of a MultiMesh share one mesh LOD level at a time — [Mesh LOD](https://docs.godotengine.org/en/stable/tutorials/3d/mesh_lod.html)
- The editor has a built-in "Populate surface" tool for MultiMeshInstance3D with random rotation, tilt and scale — [Using MultiMeshInstance3D](https://docs.godotengine.org/en/stable/tutorials/3d/using_multi_mesh_instance.html)
- Agent-found traps: a MultiMeshInstance3D whose mesh comes from a GLB "does NOT render after pack+save (mesh resource reference lost during serialization)"; call `Mesh.duplicate()` before freeing the source GLB instance; set `custom_aabb` to cover the whole area or "the MultiMesh gets frustum-culled when the camera moves to edges"; it has no `set_surface_override_material()`, use `material_override` — [godogen GDScript-era quirks](https://github.com/htdt/godogen/blob/93013e1dc4a96785794e44a691dd48d3da3ee9da/skills/godogen/quirks.md)
- ProtonScatter (MIT, 2,997 stars) places assets "in a procedural, non-destructive way" through a modifier stack (create points on a grid, randomly or along an edge; project onto colliders), `ScatterItem` nodes and box/sphere/path `ScatterShape` domains that can be negative; the GitHub repository is a mirror of Codeberg, its last tagged release is 4.0 (2023-10-23), and commits continue ("fix compatibility issue with 4.7", 2026-07-26) — [ProtonScatter](https://github.com/HungryProton/scatter)
- Spatial Gardener (MIT, 1,311 stars) paints foliage and props on any 3D surface and is implemented in GDScript; last release v1.4.1 and last commit 2025-03-05 ("Convert to Godot 4.4") — [Spatial Gardener](https://github.com/dreadpon/godot_spatial_gardener)

#### Terrain3D
- A C++ GDExtension terrain (MIT, 4,312 stars, pushed 2026-09-30): terrains from 64×64 m to 65.5×65.5 km in regions, up to 32 textures, up to 10 mesh LODs, "Foliage instancing, with up to 10 levels of detail, and a shadow impostor", sculpting, holes, texture and colour painting, heightmap import — [Terrain3D](https://github.com/TokisanGames/Terrain3D)
- v1.0.2 (2026-05-19) "Supports Godot 4.4-4.6+"; Windows and Linux fully supported; Compatibility renderer supported since Terrain3D 1.0 with Godot 4.4; web export "very experimental" — [v1.0.2 release](https://github.com/TokisanGames/Terrain3D/releases/tag/v1.0.2-stable), [platform support](https://terrain3d.readthedocs.io/en/stable/docs/platforms.html)

#### CSG for block-outs
- "The CSG nodes in Godot are mainly intended for prototyping. There is no built-in support for UV mapping or editing 3D polygons"; the docs point to FuncGodot and Cyclops Level Builder for level design; CSG is implemented with the Manifold library; "make sure CSG geometry remains relatively simple, as complex meshes can take a while to process" — [Prototyping levels with CSG](https://docs.godotengine.org/en/stable/tutorials/3d/csg_tools.html)
- Godot 4.7 adds automatic smoothing for CSG nodes with a configurable angle — [4.7 changelog, GH-116749](https://github.com/godotengine/godot/blob/4.7/CHANGELOG.md)

#### Decals
- "Decals are only supported in the Forward+ and Mobile renderers, not the Compatibility renderer. If using the Compatibility renderer, consider using Sprite3D as an alternative" — [Using decals](https://docs.godotengine.org/en/stable/tutorials/3d/using_decals.html)

#### Import pipeline automation
- glTF 2.0 is the recommended format; `.blend` files import by calling Blender to export glTF — [Available 3D formats](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/available_formats.html)
- Name suffixes in the source file drive import: `-col`, `-convcol`, `-colonly`, `-convcolonly` (collision), `-occ`, `-occonly` (occluders), `-navmesh`, `-rigid`, `-vehicle`, `-wheel`, `-noimp` (drop node), `-loop`/`-cycle` (animation), and material suffixes `-alpha` and `-vcol` — [Node type customization using name suffixes](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/node_type_customization.html)
- Scene import options include root type and scale, Ensure Tangents, Generate LODs, Create Shadow Meshes, light-baking mode with lightmap UV2 generation, animation import with trimming and FPS, and an Import Script path — [Import configuration](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/import_configuration.html)
- "A special script to process the whole scene after import can be provided. This is great for post-processing, changing materials, doing funny stuff with the geometry"; it is a `@tool` script extending `EditorScenePostImport` whose `_post_import(scene)` must return the scene — [Import configuration](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/import_configuration.html), [EditorScenePostImport class](https://docs.godotengine.org/en/stable/classes/class_editorscenepostimport.html)
- The Advanced Import Settings dialog sets per-node options (skip import; generate physics body with static/trimesh/convex/decomposed shapes; generate navmesh; generate occluder with simplification distance) and per-mesh options (save to external file, shadow mesh, lightmap UV, LODs), and material replacement and animation clips — [Advanced Import Settings](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/advanced_import_settings.html)
- Settings are stored in an `<asset>.import` file next to each source file, which should be committed; several files can be selected and reimported with only ticked parameters changed; a changed MD5 triggers automatic reimport — [Import process](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/import_process.html)
- A glTF file can be imported as an AnimationLibrary only, so that one set of animations serves several characters — [Import configuration](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/import_configuration.html)
- Run-time loading with `GLTFDocument`/`GLTFState` works in exported projects, but the docs warn: "Do not use this runtime loading approach to load resources that are part of the project" — [Runtime file loading and saving](https://docs.godotengine.org/en/stable/tutorials/io/runtime_file_loading_and_saving.html)
- Godot 4.6 added MultiMesh objects to the Advanced Import Settings dialog; 4.7 exposes import flags on GLTFDocument — [4.6 changelog, GH-113206](https://github.com/godotengine/godot/blob/4.6/CHANGELOG.md), [4.7 changelog, GH-115788](https://github.com/godotengine/godot/blob/4.7/CHANGELOG.md)
- Agent-found traps when building scenes from GLBs in code: every node needs `owner` set to the scene root or it is silently dropped on save, but recursing into an instanced GLB "inlines all its meshes as text → 100MB+ `.tscn`"; "count nodes before packing, `Instantiate()` the PackedScene after, and compare counts"; use primitive collision shapes from the AABB, "never `CreateTrimeshShape()`/`CreateConvexShape()` on imported meshes (drops to <1 FPS)"; a `.gdignore` in a directory makes the importer skip it silently — [godogen engine guide](https://github.com/htdt/godogen/blob/master/engines/godot.md)

#### LOD, HLOD and culling
- Mesh LOD is generated automatically on import (meshoptimizer) for glTF, `.blend`, Collada and FBX, selected by screen-space error; tunable with `mesh_lod/lod_change/threshold_pixels` and per-node `lod_bias`; "may occasionally introduce rendering issues (especially in skinned meshes)" — [Mesh LOD](https://docs.godotengine.org/en/stable/tutorials/3d/mesh_lod.html)
- For meshes built in code, `ImporterMesh.generate_lods()` generates the LODs — [ImporterMesh class](https://docs.godotengine.org/en/stable/classes/class_importermesh.html)
- Godot 4.6 switched LOD generation to iterative simplification and enabled component pruning — [4.6 changelog, GH-110027 and GH-110028](https://github.com/godotengine/godot/blob/4.6/CHANGELOG.md)
- Visibility ranges work on any GeometryInstance3D (MeshInstance3D, MultiMeshInstance3D, particles, Label3D, Sprite3D, CSG): begin/end distances with margins and a fade mode; the Visibility Parent property hides children when the parent is shown, so that a group of detailed meshes is replaced by one simplified mesh at distance — [Visibility ranges (HLOD)](https://docs.godotengine.org/en/stable/tutorials/3d/visibility_ranges.html)
- Occlusion culling is CPU software rasterisation with Embree against baked OccluderInstance3D geometry; it is "most effective in indoor scenes with many smaller rooms"; MultiMeshInstance3D, particles and CSG are not baked as occluders; moving occluders is expensive — [Occlusion culling](https://docs.godotengine.org/en/stable/tutorials/3d/occlusion_culling.html)
- "Large worlds may need to be built in tiles that can be loaded on demand as you move around the world"; visibility ranges are "a good way to set up impostors for distant geometry" — [Optimizing 3D performance](https://docs.godotengine.org/en/stable/tutorials/performance/optimizing_3d_performance.html)
- The renderer comparison says of unlisted features: "If a feature is not listed here, it is available in all renderers"; mesh LOD, visibility ranges, occlusion culling, MultiMesh and GridMap are not listed — [Renderers](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)

#### What the Compatibility renderer, web and mobile take away
- Web: "Forward+/Mobile are not supported on the web platform"; only Compatibility over WebGL 2.0; WebGPU is not supported; single-threaded export is the default since 4.3; GDExtensions must be compiled for web and need cross-origin isolation headers; C# projects cannot be exported to web — [Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)
- Not supported in Compatibility: PCSS soft shadows, light projector textures, VoxelGI, SDFGI, SSIL, volumetric fog, screen-space reflections, sub-surface scattering, TAA, FSR2, FXAA, SMAA, MSAA for 2D, screen-space roughness limiter, CompositorEffects, compute shaders, the normal/roughness buffer, debanding, decals, particle trails, particle SDF collision, depth-of-field blur, HDR 2D viewport, HDR output and RenderingDevice access — [Renderers](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)
- Supported in Compatibility: depth and height fog, tonemapping, glow, colour adjustments, MSAA 3D, SSAA, screen texture and depth texture access, "custom post-processing with fullscreen quad", ReflectionProbes (2 per mesh), rendering of baked lightmaps (baking needs RenderingDevice hardware), SSAO — [Renderers](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)
- Details: Compatibility SSAO is "a simplified version" available "Since Godot 4.6" with only radius and intensity; Compatibility glow "uses a different implementation" without Levels, Normalized, Strength, Blend Mode, Mix or Map — [Environment and post-processing](https://docs.godotengine.org/en/stable/tutorials/3d/environment_and_post_processing.html)
- Lights: Compatibility renders up to 8 OmniLights + 8 SpotLights per mesh (adjustable in Rendering > Limits > OpenGL "at the cost of performance and longer shader compilation times"); Mobile has a fixed limit of 8 + 8 per mesh and 256 per view; Forward+ 512 per cluster — [Lights and shadows](https://docs.godotengine.org/en/stable/tutorials/3d/lights_and_shadows.html)
- Precision: Compatibility renders to RGBA8 with 24-bit depth without reverse Z; Mobile RGB10A2; Forward+ RGBA16F with 32-bit depth; without internal HDR, banding shows on smooth gradients — [Renderers](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html), [3D rendering limitations](https://docs.godotengine.org/en/stable/tutorials/3d/3d_rendering_limitations.html)
- Shader stutter: ubershaders, pipeline precompilation and the shader baker apply "only … to the Forward+ and Mobile renderers, not Compatibility" — [Reducing stutter from shader compilations](https://docs.godotengine.org/en/stable/tutorials/performance/pipeline_compilations.html)
- AreaLight3D (4.7): "limited support in the Mobile and Compatibility renderers … In Compatibility, area lights cannot cast shadows"; textured area lights are not supported in Compatibility — [AreaLight3D class](https://docs.godotengine.org/en/stable/classes/class_arealight3d.html), [Lights and shadows](https://docs.godotengine.org/en/stable/tutorials/3d/lights_and_shadows.html)
- "New features" policy: "All new features are added to Forward+ … Some new rendering features are added to Compatibility. Features are added after Mobile and Forward+" — [Renderers](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)
- Rust on the web: godot-rust's web export is "experimental"; it needs nightly Rust with `-Zbuild-std`, the `wasm32-unknown-emscripten` target, a specific Emscripten version, export templates with Extensions Support, and separate threaded and `nothreads` builds; panics cannot be caught and abort the game; Firefox support is "more limited compared to Chromium-based browsers" — [godot-rust book: Export to Web](https://godot-rust.github.io/book/toolchain/export-web.html)
- Android and iOS support in godot-rust is also described as experimental with "documentation and tooling … still lacking" — [gdext README](https://github.com/godot-rust/gdext)
- A real web-export snag in an agent-built game: "an environment map / SSR support gap" — [Exonix write-up](https://www.top3d.ai/learn/claude-godot-mcp-3d-game)

#### A geometry trap for code-built meshes
- "Godot treats CLOCKWISE winding as the front face, which is the opposite of the OpenGL convention most mesh-generation code is written against, and getting it backwards produces no error, no warning, and a perfectly healthy-looking node" — [Beckett forum post](https://forum.godotengine.org/t/beckett-zero-sidecar-mcp-server-for-godot-4-2-the-ai-sees-and-optionally-playtests-your-game/141177/7)
- `ArrayMesh` built in code must have normals generated to receive shadows; "Without it … shadows silently vanish" — [godogen engine guide](https://github.com/htdt/godogen/blob/master/engines/godot.md)

### Inferences
- A placement grid driven by data maps directly onto GridMap: a MeshLibrary per style pack (built from code or exported from a kit scene) and `set_cell_item` calls give per-octant batching, collision and navigation without hand-written instancing. Switching style live then means swapping the `mesh_library`, provided item ids are kept stable across packs. Because GridMap is not a GeometryInstance3D, it cannot use visibility ranges or per-instance material overrides, so distant-city simplification would need separate HLOD meshes outside the GridMap (inference from the class note; I found no source describing GridMap combined with HLOD).
- Since automatic instancing exists only in Forward+, a design that relies on thousands of individual MeshInstance3D kit pieces will lose its batching the moment the project is exported to web (Compatibility) or run with the Mobile renderer; GridMap or explicit MultiMesh keep batching on every renderer.
- Style packs that depend on decals, light projectors, SSR, depth of field, compositor effects or outline shaders that read the normal-roughness buffer cannot be carried to the web unchanged. Cel-shading done in material shaders, fog, glow (limited), SSAO (limited) and full-screen-quad post-processing using screen and depth textures survive.
- Import-time automation is the engine-native replacement for hand-rolled fix-up code: one `EditorScenePostImport` script, shared by all GLBs in a kit through multi-file reimport, can assign materials, add collision from name suffixes, set visibility ranges and save meshes externally. The project has 413 GLBs with `.import` files, so this applies today.
- An imported-kit workflow needs the import step run headlessly after every asset change (`godot --headless --import`), as godogen prescribes and as the project's own README already does; Exonix needed the same command for a different reason (refreshing the script class cache) because it loads assets at run time and so forgoes import-time LODs, shadow meshes and post-import scripts altogether.

### Gaps
- I found no documented Godot city project that combines GridMap, HLOD and occlusion culling, and no measurements of GridMap performance at city scale.
- Terrain3D's support for Godot 4.7 is not stated in its latest release notes (which predate 4.7).
- Spatial Gardener has had no commits since March 2025; its behaviour on 4.6 and 4.7 is unverified.
- The docs describe mobile only through the renderer table; I did not find current guidance on memory or draw-call budgets for mobile or web.
- Lighting, shader look development, asset kits and AI generators are out of scope here and covered by other researchers.

## 5. Writing GDScript and gdext with LLMs: pitfalls, resources and testing

### Takeaway
By 2026 the frontier models write correct Godot 4 GDScript most of the time; the remaining failures are GDScript's Variant type inference, occasional Godot 3 idioms, run-time versus build-time API confusion and silent failures that compile cleanly, and they are cured by engine-in-the-loop checks (parser, import, tests) rather than by documentation dumps. There is no official `llms.txt`; the reliable ground truth is the installed binary's own API dump. gdext is a separate hazard because its API was reshaped in each of three minor releases between June 2025 and March 2026 (0.3, 0.4, 0.5), each with its own migration guide.

### Cited Findings

#### How good are current models at GDScript?
- The godogen author in March 2026: "LLMs barely know GDScript. It has ~850 classes and a Python-like syntax that will happily let a model hallucinate Python idioms that fail to compile" — [Show HN thread](https://news.ycombinator.com/item?id=47400868)
- Contradicted by users in the same thread: "I've gotten completely fine GDScript and even decent perfectly functional if placeholder-quality TSCN files from Opus 4.5, 4.6, and Sonnet 4.6 with very little issue and no special tricks; just a CLAUDE.md file, the project itself, and going through plan mode … Every once in a while … I get something appropriate for Godot 3 instead of Godot 4, but never Python" — [HN comment](https://news.ycombinator.com/item?id=47407325); "I've never had it hallucinate stuff, and I've barely seen it look at docs" — [HN comment](https://news.ycombinator.com/item?id=47406299)
- A July 2026 benchmark gave the same original Godot 4 typed-GDScript task ("Conveyor Courier") to 18 CLI models, graded headlessly against hidden tests over three repetitions (300 points): claude-sonnet-5 290, swe-1.7 280, gpt-5.5 280, claude-haiku-4-5 86; four models passed the hidden tests in every repetition. Observed defects: untyped nested arrays and type warnings, spec-detail errors, "dead mouse" from `ColorRect` mouse filters, missing font glyphs, a board that did not render, run-to-run non-determinism. A `gdscript-quality` skill (type annotations, typed collections, zero warnings) raised one model from 270 to 300 — [benchmark article, 2026-07-18](https://dev.to/kiou_ouba_afbd120335456f3/which-model-should-your-agent-outsource-to-benchmarking-18-cli-child-models-on-the-same-godot-game-pa9), [repository](https://github.com/oubakiou/godot-llm-gamebench)
- A vendor's side-by-side test (May 2026) found an October-2023-cutoff model writing Godot 3 forms (`KinematicBody`, `Spatial.translation`, `onready var`, old `connect`) while Claude Opus 4.7 wrote the Godot 4 forms for all six cases (vendor) — [Ziva blog, 2026-05-15](https://ziva.sh/blogs/claude-godot)
- An MCP author still frames the problem as structural: "Models trained on data skewed towards Godot 3 hallucinate deprecated APIs (`yield` instead of `await`, `KinematicBody` instead of `CharacterBody3D`, `export var` instead of `@export var`)" — [godot-forge README](https://github.com/gregario/godot-forge)

#### Concrete GDScript traps recorded by an agent pipeline
- Type inference with `:=` fails on Variant-returning calls: `load()` returns Resource (type the variable as PackedScene), `instantiate()` returns Variant (use `=` or an explicit type), polymorphic maths functions (`abs`, `sign`, `clamp`, `min`, `max`, `floor`, `ceil`, `round`, `lerp`, `smoothstep`, `move_toward`, `wrap`, `snappedf`, `randf_range`, `randi_range`) and array or dictionary element access return Variant — [godogen GDScript-era quirks](https://github.com/htdt/godogen/blob/93013e1dc4a96785794e44a691dd48d3da3ee9da/skills/godogen/quirks.md)
- Run-time traps from the same list: `init()`/`setup()` called before `add_child()` leaves `@onready` variables null; `get_path()` is a built-in Node method and cannot be redefined; changing a collision shape's `disabled` inside `body_entered` needs `set_deferred`; `_ready()` of instantiated nodes does not fire during `_initialize()` of a `--script` SceneTree; autoloads cannot be referenced by name from SceneTree scripts; `preload()` fails for resources generated later in the same run; collision layers are bitmasks, not UI layer numbers; a new body's `collision_mask = 1` misses layers 2+ "with no error" — [godogen GDScript-era quirks](https://github.com/htdt/godogen/blob/93013e1dc4a96785794e44a691dd48d3da3ee9da/skills/godogen/quirks.md)
- The author's assessment when moving to C#: "Death by a thousand paper cuts. The type inference system creates a steady stream of subtle errors … The `:=` operator is the default instinct but fails on ~15 common API patterns"; C# replaced per-file `--check-only` validation with one `dotnet build`, at the price of unreliable C# enum names because "training data is predominantly GDScript" — [GDScript vs C# comparison](https://github.com/htdt/godogen/blob/master/docs/gdscript-vs-csharp.md)
- The remaining guide keeps only silent failures: "Most Godot behavior the model already knows; these few fail with no error" — [godogen engine guide](https://github.com/htdt/godogen/blob/master/engines/godot.md)

### Inferences
- For GDScript, the documentation problem has largely been overtaken by model progress during 2026; what still pays is a short project rules file (typed GDScript, no `:=` on Variant-returning calls, the silent-failure list) plus an automatic parse check after every write. godogen's own trajectory — building a docs converter, a quirks database and a lookup skill, then deleting all three within four months — is the strongest evidence.
- For gdext the opposite holds: an agent's training data necessarily mixes v0.2 to v0.5 idioms (and the older Godot 3 `gdnative` crate), and the 0.4 and 0.5 releases both renamed core APIs. The compiler catches these, so the cost is iteration time rather than silent bugs; pinning the crate version in the rules file and pointing the agent at the migration guides and docs.rs for that version is the available mitigation. I found no skills or rules files written specifically for gdext.
- GDScript's lack of a single whole-project compile step is why hooks matter more there than in Rust or C#: one `cargo build` or `dotnet build` validates everything, while GDScript needs per-file `--check-only` or a headless import/boot.
- GUT and gdUnit4 are both current for 4.7, but agent write-ups show a preference for tiny custom runners, probably because the frameworks' editor-plugin installation and coroutine-heavy tests add failure modes; gdUnit4's scene runner is the only one of the two with built-in input simulation.

### Gaps
- No public, version-pinned Godot API dump for LLMs is maintained by the Godot project; Context7's index is third-party and its version coverage is not stated.
- I found no rules file, skill or benchmark for gdext with coding agents, and no report of LLM error rates on gdext specifically.
- The benchmark and HN evidence concerns small tasks (hundreds to low thousands of lines); I found no measurement on a large GDScript codebase.
- The vendor comparison of models on Godot 3 versus 4 forms covers six API cases and discloses no methodology.

## 6. What did Godot 4.5, 4.6 and 4.7 add for visuals, animation, IK and large scenes?

### Takeaway
The three releases between September 2025 and June 2026 rebuilt Godot's 3D character tooling — bone constraints in 4.5, a full IK solver family in 4.6, AnimationTree optimisation and cyclic blend-space sync in 4.7 — and improved look and scale through stencil buffers, bent normals, SMAA, a shader baker, overhauled SSR, better automatic LODs, simple SSAO for the Compatibility renderer, area lights, HDR output and nearest-neighbour 3D scaling. There is still no IK tutorial in the manual; the IK nodes are documented only in the class reference.

### Inferences
- For stiff character movement the relevant additions are in 4.6: `TwoBoneIK3D` (deterministic, needs a pole target) is the natural node for foot planting on a humanoid leg, `LimitAngularVelocityModifier3D` damps snapping, and `BoneTwistDisperser3D` fixes forearm and shin twist. They are skeleton modifiers that run after animation, so they need a skinned rig and clips to modify; they do not replace locomotion animation.
- Because the IK family is nine months old and has no manual tutorial, models with 2025 training cut-offs are likely to propose the older `SkeletonIK3D` (still present but marked deprecated in the 4.7 class reference) or third-party add-ons; pointing the agent at the class reference for the installed version is necessary here even if it is not for general GDScript.
- For a stylised city the most useful visual additions are 4.6's Compatibility SSAO and AgX controls (they survive a web export), 4.7's nearest-neighbour 3D scaling (a pixel-art-in-3D look without custom shaders) and 4.5's stencil buffer (outlines and x-ray effects). Area lights and HDR output are in practice desktop features.
- The project's `project.godot` declares `config/features` "4.6" with the Forward+ renderer while the engine installed on the workstation is 4.7.2 (both read locally on 2026-10-01), so everything listed for 4.5 and 4.6 is available to the project as it stands and the 4.7 additions are available on this workstation's engine.

### Gaps
- Items cited with a pull-request number were read in the changelogs; items without one (for example octahedral probe maps, glow blending order, the MeshLibrary editor, HDR output platforms) were confirmed only by text search of the official release pages.
- Renderer support for stencil, SMAA and nearest-neighbour scaling in the Compatibility renderer was not verified item by item beyond the renderer comparison table.
- I did not find performance measurements for the new IK solvers or for AnimationTree after the 4.7 optimisation.
- Godot 4.8 development snapshots were not examined.
